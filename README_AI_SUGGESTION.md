`GEMINI.md`（またはAIアシスタント向けガイドライン）に記述された指針に基づき、プロジェクトの品質（コード品質、保守性、テスト網羅率、開発プロセス）を大幅に向上させるための**具体的な改善案（アクションプラン）**を作成しました。

もし実際の`GEMINI.md`に特定のルールがある場合は、それに応じて微調整しますので適宜共有してください。以下は、一般的な開発運用・AI活用におけるベストプラクティスを網羅した品質向上計画です。

---

# プロジェクト品質向上・具体的アクションプラン

## 1. 静的品質とコード規約の自動強制（Static Quality）
AIがコードを生成する際、および人間がコードを書く際の「揺らぎ」をなくし、常に一定以上の品質を保ちます。

*   **1.1 Strict（厳格）な型定義と静的解析の導入**
    *   **具体案:** `tsconfig.json` で `strict: true` を有効化。Pythonの場合は `mypy` や `pyright` を厳格モードで導入。
    *   **GEMINI.mdへの反映:** 「`any` 型の使用禁止」「型定義なしでの関数追加を禁止」をAIへの明示的なルールとして追加。
*   **1.2 統一フォーマッタ / リンターの導入とGitフックの自動化**
    *   **具体案:** Biome, ESLint, Prettier, Ruff などを導入し、`Husky` + `lint-staged` でコミット時に強制実行。
    *   **効果:** 構文エラーやフォーマット違反があるコードがリポジトリに入り込むのを100%防ぎます。

## 2. AI連携型の自動テスト戦略（Dynamic Quality）
品質保証の要となるテストの作成を、AI（Gemini）と協力して高速化・自動化します。

*   **2.1 カバレッジ目標の設定（例: 80%以上）**
    *   **具体案:** ユニットテスト（Jest, Vitest, Pytestなど）の自動実行環境を構築。
    *   **GEMINI.mdへの反映:** 「機能を1つ作成・修正したら、必ず対応する単体テスト（正常系・異常系・境界値）を同時に生成・更新すること」を義務化。
*   **2.2 E2E / インテグレーションテストの自動化**
    *   **具体案:** Playwrightなどを導入し、クリティカルなユーザーフロー（ログイン、決済、主要機能）のテストを自動化。

## 3. CI/CDパイプラインによる「品質ゲート（Quality Gate）」の構築
個人の環境に依存せず、プルリクエスト（PR）単位で自動的に品質チェックを行わせます。

*   **3.1 GitHub Actions (またはGitLab CI) の強化**
    *   PR作成時に以下を自動実行し、すべてPassしないとマージ不可（Branch Protection）にする。
        1.  型チェック (Type Check)
        2.  リンター・フォーマッタチェック (Lint & Format)
        3.  全テストの実行とカバレッジレポート出力 (Test)
        4.  ビルドチェック (Build)
*   **3.2 AIによるPR自動レビューの導入**
    *   **具体案:** Gemini APIを活用したGitHub Actionを組み込み、PR作成時にAIがセキュリティ脆弱性・パフォーマンス懸念・可読性を自動レビューする仕組みを導入。

## 4. `GEMINI.md` 自体の最適化（コンテキスト管理）
AI（Gemini）が常にプロジェクトの正確な文脈・設計思想を理解してコードを生成できるようにします。

*   **4.1 「やってはいけないこと（Negative Constraints）」の明確化**
    *   **具体案:** 推奨事項だけでなく、禁止事項を明記する。
        *   例: 「直接DBクエリをコントローラーに書かない（必ずRepository層を経由すること）」
        *   例: 「外部ライブラリを新しく追加する場合は必ず事前に理由を明記すること」
*   **4.2 アーキテクチャ図・ディレクトリ構造の明記**
    *   プロジェクトの層構造（Clean Architecture, DDD, MVCなど）と、ファイル配置ルールを`GEMINI.md`に明記し、AIが間違った場所にコードを作成するのを防ぐ。

## 5. ドキュメントと設計の同期化（Maintainability）
コードの変更に合わせてドキュメントが古くなる「ドキュメントの腐敗」を防ぎます。

*   **5.1 ADR（Architecture Decision Records）の運用**
    *   重要な技術的決断（ライブラリ選定、アーキテクチャ変更など）を行う際、`docs/adr/` 配下に短文の記録を残すルールにする。
*   **5.2 OpenAPI (Swagger) などのスキーマ駆動開発**
    *   API設計を先に確定させ、そこから型定義やフロントエンドのAPIクライアントコードを自動生成する。

### 次のアクションのご提案
より具体的にプロジェクトに合わせた提案を作成するため、以下のいずれかを実施可能です。

1. **現在の `GEMINI.md` の内容を貼り付けていただく**
   → 記述を直接添削し、より精度が高まるプロンプト／指示文にリファクタリングします。
2. **現在の技術スタック（言語・フレームワーク・CIツール）を教えていただく**
   → 設定ファイル（`tsconfig.json`, `eslintrc`, `github/workflows/*.yml` など）の具体的なサンプルコードを作成します。
