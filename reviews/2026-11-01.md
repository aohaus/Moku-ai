### MR-002: ページを閉じた時のアップロードのあと、Moint が二重に数えられる

**証拠(コード)**
- `flushOnHide()` は `keepalive` で `PUT /save` を送り、返事が来たら `setSyncState(user, res.rev, local)` で基準を更新する(`moku-account.js:552-553`)。ページを移動した後は返事の `.then` が実行されないので、サーバーは rev R+1 なのに、端末の基準は rev R・古い財布のまま残る。
- `keepMerged()` には返事が消えた時のための `moku:sync:pending` があるが(`:521-526`)、`flushOnHide()` は pending を書かない。
- 次に同期する時、端末とクラウドの両方で財布が変わっていると、`mergeWallet()` が `r + (l − b)`(`:220`)で計算する。`r` にはこの端末から送った増えた分がもう入っているので、その分を2回数える。
- ゲームページ(`data-mode="background"`)は開いた時に同期しない(`boot()` は `mode === 'full'` のときだけ `syncNow`、`:1183-1187`)。`pageshow`(bfcache から戻った時)で同期する処理もない(`grep pageshow` の結果なし)。

**再現(ローカルのモック `npm run dev` + Playwright、本番には触れていない)**

```
1 hub synced: wallet 100 st.rev 1
2 earned 50 in Moku Bridge: wallet 190      (初回ギフト 40 + 50)
3 moved to Moku Drop: st.rev 1 PUT statuses so far 200   ← アップロードは成功したのに基準は rev 1 のまま
4 earned 30 in Moku Drop: wallet 220
5 back on hub after sync: wallet 310        ← 正しくは 220。Bridge で増えた 90 が二重に足された
  cloud wallet 310
```

再現に使った手順: ハブ → Moku Bridge で稼ぐ → (ハブを通らずに)Moku Drop を開いて稼ぐ → ハブを開く。
間にハブを**新しく読み込む**と、そこでの同期で基準が直るので起きない(同じスクリプトで確認した)。

**影響**
- 次のような場合に、ハブを新しく読み込まずに続けて遊ぶと、Moint が増える(減る方向でも同じ計算になる)。
  - iOS Safari のスワイプで戻った時に、ハブがキャッシュ(bfcache)から再表示された
  - iOS でタブが裏で捨てられた
  - ホーム画面のブックマークからゲームを直接開いた
- どれくらい起きるかは端末次第で、bfcache から戻った時の再現はこの環境ではできていない(ヘッドレス Chromium は bfcache を使わなかった)。そのため確信度は Medium。
- 財布だけでなく、両方で変わったキーは「ソフトキーはこの端末を採用」「Closet は持ち物をまとめる」なので、影響が大きいのは財布だけ。

### MR-001: PIN のロックアウトの回数カウントが同時のリクエストで数え漏れる

**証拠(コード)**
- `login()` はユーザーを読み(`accountApi.js:575`)、PIN を確かめ(scrypt。時間がかかる)、`failCount = (user.failCount || 0) + 1` を計算して `store.updateUser(loginId, { failCount, lockedUntil })` で書き戻す(`:583-586`)。
- `updateUser` はただの `SET`(条件なし。`accountStore.js:105-112`)。同時に処理している間は全部が同じ古い `failCount` を読む。
- ロックされていない側の書き込みは `lockedUntil: user.lockedUntil || 0`(`:585`)。古い値を読んだリクエストが後から書くと、別のリクエストが付けたロックを **0 に戻してしまう**可能性もある(今回の再現では起きなかった)。

**再現(本物の `createAccountApi` + `memoryStore`。ストアの呼び出しに 5〜25ms の遅延を入れて DynamoDB の往復をまねた)**

```
sequential 5 wrong -> 429 locked            ← 1つずつ送れば5回でロック(正しい)
sliding: tries 501 found null 429s 445      ← 8ms おきに送ると、ロックされるまでに 56 回試せた(501 − 445)
failCount 5 lockedUntil>now true
```

**影響**
- 4桁の PIN(弱い PIN を除いて約9,980通り)に対して、ロック1回あたり試せる数が5回から約50回に増える。ロック時間は 15分→30分→…→24時間と伸びるので、すぐに破られるわけではない。それでも「5回でロック」という設計の前提が崩れている。
- ただし、Player ID を知っている人(兄弟・友達)が意図して狙う場合に限られる。API Gateway の制限(`/auth/login` は全体で 10/秒)もあるので、Medium とした。

### MR-003: `listUsers()` がテーブル全体を Scan する

**証拠(コード)**
- `accountStore.js:144-162`: `ScanCommand` + `FilterExpression: "sk = :p"`。DynamoDB の Scan は、条件で除く前に**読んだ量のすべて**を課金・時間に数える。コメントには「≤ 100 accounts なら Scan で十分」とあるが、同じテーブルには次も入っている(`accountStore.js:12-24`)。
  - `LOG#<日付>`: 1日の件数に上限なし、90日残る
  - `ERR`、`MATCH#`、`CHAL#`、`ROOM#`、`ROOM# / P#`(Moyomoyo の盤面)、`PLAYER#…`
- 呼ばれる場所:
  - `GET /players`(ハブを開くたび、最大1分キャッシュ。`moku-account.js:1042-1043`)
  - `GET /players/kin`
  - `findOpponent`(対局・チャレンジ・部屋の招待)
  - 管理画面の一覧(`listSaves` も同じ Scan)
- Lambda の Timeout は 5秒(`template.yaml:10`)。

**影響(見積もり。本番のテーブルの大きさは見ていないので未検証)**
- 例えば30人が1日20回ずつセーブすると、ログは 600件/日 × 90日 ≈ 5.4万件(1件 0.5〜1KB)。この場合、1回の Scan は約30〜50MB になり、1MB ずつ数十回の往復で1〜3秒、1回あたり数千 RRU かかる。
- ログが増えるほど、ハブの Players・Hollow・Achievements・対戦相手探しが遅くなる。いずれタイムアウトすると「友達が出ない」「対局が作れない」になる。費用も遊ぶ回数に比例して増える。
